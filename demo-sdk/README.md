# Tracker CE demos (`.ptdemo`)

Full-screen demoscene effects that live on the SD card, not in the firmware.

## Running a demo

1. Copy `*.ptdemo` files to `/Demos` on the SD card (the folder is created the first time you open the menu).
2. On the Tracker: **Config → Info → Demos**, pick a file with the jog wheel or Up/Down, press **Run** (Cancel goes back).
3. **Shift** leaves the demo and returns to Config. Nothing else responds while a demo runs (the power button still works). Interactive demos (see below) are left with **Shift+Pattern** instead.

The firmware stops the current song before a demo starts. A demo can bring its own music (see below).

## Writing a demo

One C file, no libc. Everything comes through the host API in `tracker_demo.h`:

| Entry point | When |
|---|---|
| `int32_t demo_init(const PtDemoHostApi* host, void* scratch, uint32_t scratch_size)` | once; upload textures, return 0 |
| `void demo_frame(uint32_t time_ms)` | every panel frame; emit FT81x display-list words with `host->dl()` |
| `void demo_exit(void)` | optional, on Shift |

The firmware opens each frame with `VERTEX_FORMAT(0)` and a black clear, and closes and shows it after `demo_frame` returns. Use the `PTD_*` macros for the words. Keep within about 2000 words per frame. The included demo uses about 325.

Metadata goes in comments at the top of the file:

```c
// PTDEMO_NAME: Oldskool
// PTDEMO_AUTHOR: you
// PTDEMO_SCRATCH: 8192        // working RAM, max 384 KB
// PTDEMO_FLAGS: IMX_ONLY      // only if code+bss > 32 KB
// PTDEMO_FLAGS: INPUT         // interactive: all input + saving (API 3)
// PTDEMO_MOD: tune.mod        // optional music, next to the source file
```

Build (needs `arm-none-eabi-gcc`):

```sh
python3 ptdemo_builder.py demos/oldskool.c -o build/Demos/oldskool.ptdemo
```

### What you get

| | |
|---|---|
| Graphics RAM (RAM_G) | `host->ramg_base` .. `+ramg_size` (700000..1040000, 340 KB, on this firmware). Writes outside are ignored. |
| Bitmap handles | `host->first_bitmap_handle` .. `+bitmap_handle_count-1` (8..14) |
| ROM fonts | read metrics from `PTD_ROM_FONT_TABLE_POINTER`; see `oldskool.c` |
| Code + bss | up to 128 KB (the builder asks for `IMX_ONLY` above 32 KB, so a demo says it needs a Tracker+/Mini) |
| Files | `host->read_file("tex.bin", …)`: relative paths resolve next to the `.ptdemo` (call from `demo_init` only) |
| Pads | `host->pad_light(pad, level)` |

### Music

Put a 4-channel ProTracker module next to the source and name it with `// PTDEMO_MOD:`. The builder appends it to the `.ptdemo`, so one file carries the whole production. The firmware plays it with its own ProTracker 2.3D replayer, the one the tracker uses. It plays from its own module memory, so the song you're editing is never touched.

- **Start and stop:** the music starts with the first frame (`time_ms` 0, position 0) and stops when the demo ends.
- **Sync:** `host->mod_state(&s)` gives position, pattern, row, tick, speed, BPM and a VU value per channel. It also gives a `hits` counter per channel that goes up by one for every note started, which is the easy way to flash something on a drum hit.
- **Control:** `host->mod_play(position)` and `host->mod_stop()` restart or stop the music. `host->mod_load("part2.mod")` swaps in another module between parts; it stalls briefly, so don't call it every frame.
- **Limits:** the usual .mod limits apply: 4 channels, up to 100 patterns, samples up to 64 KB.

The example `demos/oldskool.c` flashes the copper bars on kick hits, pumps the cube on snares and swings the scroller with the arpeggio channel. Its tune `demos/oldskool.mod` is generated by `tools/make_oldskool_mod.py`, so it is free to use.

Music needs host API version 2. The builder records that in the header, and firmware that is too old refuses the demo with "Needs newer firmware". A demo without music still runs on API 1 firmware.

### Input and saving (API 3)

A demo with `// PTDEMO_FLAGS: INPUT` (flags combine: `IMX_ONLY, INPUT`) is interactive:

- **Input:** every button, pad and the jog wheel go to the demo instead of the firmware. Read them in `demo_frame` with `host->poll_input(&e)` until it returns 0. Each `PtDemoInput` is a button press/release (`index` = button number, `PTD_BUTTON_*` in `tracker_demo.h`), a pad press/release (`index` 0-47, row by row from the top left) or a jog step count (`value`, + is clockwise).
- **Leaving:** Shift is an ordinary button for the demo, so the user leaves with **Shift+Pattern**. That combination is never delivered.
- **Files:** `write_file(path, data, size)` creates or replaces a file, `list_dir(path, names, size, max)` lists the files in a folder, `file_exists(path)` and `make_dir(path)` do what they say. Paths work as for `read_file`. These, and `read_file` and `ramg_write`, may be called from `demo_frame` and `demo_exit` too; the frame just stalls while the card works.
- **Switching off:** `demo_exit` also runs when the unit is switched off while the demo runs, so save there.

The builder records API 3 for an `INPUT` demo, or one that calls the new functions, so older firmware refuses it with "Needs newer firmware".

[asciitracker](https://github.com/hannibalpeck/AsciiTracker) (`demo/asciitracker_demo.c` there) is a full interactive demo: an ASCII art editor that types with the pads and saves to `/ASCII`.

### Rules

The code runs wherever the loader puts it, and nothing patches addresses. The builder refuses anything that would need that:

- keep every global `static` (the builder also hides symbols)
- no pointers in initialized data (`static const char* names[] = {...}` fails); build tables of offsets or compute pointers at run time
- no libc calls: use `host->sinf`, `host->memcpy`, and so on

A demo runs as native code, so a crashing demo freezes the Tracker until you power-cycle it. Test new demos without unsaved work open.
